Gestor de capas geográficas

GeoJSON o Shapefile (ZIP) → PostGIS → tiles → snapshot del visor.

Cómo importar una capa
  1. Crea los metadatos con Agregar capa.
  2. En Importar capa elige la capa, el archivo y la dimensión.
  3. El worker carga la tabla en PostGIS y genera los tiles MVT.
  4. Asigna la capa a grupos/subgrupos en Taxonomía.
  5. Publica el snapshot para que el visor la muestre.

GeoJSON o ZIP con Shapefile (.shp/.dbf/.shx/.prj). El GeoJSON de respaldo queda como fallback. La versión de tiles es inmutable.

GeoJSON: máx. 100 MB. Shapefile: ZIP de máx. 200 MB con .shp, .dbf, .shx y .prj del mismo nombre.

Nuevo documento

Sube el PDF, completa la procedencia y encola la ingesta.

Cómo completar
  1. Slug: identificador único en minúsculas, números y guiones (ej. ley-glaciares).
  2. PDF: máximo 25 MB, con firma PDF válida. Se guarda en rag/inbox/.
  3. Procedencia: título, URL https://, editor, licencia y fecha.
  4. Derechos: marca la declaración solo si la licencia permite indexar el documento.
  5. Pasos: guarda metadatos → sube el PDF → Estimar para ver chunks/tokens/costo → Guardar e ingestar.

La ingesta la procesa rag-worker. Si no está activo, el trabajo queda en cola.

Máximo 25 MB. El archivo se guarda en rag/inbox/.

Documentos

Manifiesto y estado en rag.documents.

Estados de un documento
  • Ready: versión indexada y disponible para el chat.
  • Sin ingestar: está en el manifiesto pero todavía no se procesó.
  • Necesita OCR: el PDF no tiene texto extraíble.
  • Rechazado: falló la compuerta de derechos o la validación.
  • Falló: error de extracción, embeddings o base de datos.

Chunks muestra los fragmentos indexados. Quitar borra la entrada del manifiesto, no las versiones ya ingeridas.

La cola la procesa rag-worker.

Cómo funcionan los trabajos
  • Estimar: dry-run; no escribe en rag.* ni llama al proveedor.
  • Ingestar: extrae, fragmenta, embebe y escribe la versión nueva.
  • En cola: espera al worker; puedes cancelarlo.
  • Ejecutando: no se cancela a mitad de la ingesta.
  • Resultado: chunks, páginas o código de error.

Conexiones externas

Allowlist del proxy y APIs consumidas por el backend.

Gestión de conexiones
  • Variables: el panel solo muestra nombres y si están presentes; nunca lee ni guarda secretos.
  • Probar: hace una petición controlada desde el servidor y guarda HTTP, latencia y error.
  • Editar: cambia label, timeout, rate limit o si está activa. La URL y los secretos viven en el entorno.
  • Archivar: desactiva la conexión para el backend sin borrar su definición de código. Se puede reactivar cuando quieras.
  • Nueva conexión: requiere código en la allowlist del proxy y un deploy; el botón muestra los pasos, no crea URLs arbitrarias.
  • Eliminar del todo: se hace por código (registro y allowlist) y deploy; el panel no borra conexiones operativas.

Requiere código y deploy; el panel no acepta URLs arbitrarias.

Prompts versionados

Cada cambio crea una versión y activa la nueva.

Prompts del asistente

Son las instrucciones que el modelo recibe en cada consulta. Hay dos:

  • chat.system: reglas del asistente (qué puede responder, cómo citar capas y qué no inventar).
  • chat.classifier: clasifica la pregunta en dominio, intent y confianza antes de responder.

Qué hace el panel: cada guardado crea una versión nueva y activa la nueva; las anteriores quedan en el historial. Activar copia una versión histórica como versión nueva. La versión activa no se puede eliminar.

Antes de activar: corre el golden set en staging con CHAT_ROUTER_ENABLED=1 CHAT_UNAVAILABLE_ENABLED=1 y compara el acierto por tier. Si baja, no actives el cambio.

Ids que lee el chat: chat.system y chat.classifier. Guardar crea una versión nueva y la activa.

La versión anterior queda en el historial y se puede reactivar sin perderla.

Settings

Settings del chat

Parámetros que el orquestador lee en cada consulta. El panel permite editar los que tienen editable=true; el resto se muestra para diagnóstico.

  • chat.router.enabled: activa el router determinístico (evita el LLM en casos simples).
  • chat.router.min_confidence: confianza mínima para aceptar la ruta del router (0-1).
  • chat.unavailable.enabled: activa el detector de datos no disponibles.
  • chat.geojson.enabled: permite que el chat pinte capas en el mapa.
  • chat.verbose: el asistente puede nombrar tools y capas técnicas.

Tipo: string, number, boolean o json. Un valor mal escrito puede desactivar una función; si no estás seguro, no cambies un setting que funciona.

Ejemplos: chat.router.enabled, chat.router.min_confidence, chat.verbose.

boolean: true/false. number: solo números. json: objeto o array válido.

Mensajes estándar

Mensajes estándar

Texto que devuelve el chat cuando no puede responder. Viven en admin.messages y el código tiene un fallback si faltan.

  • chat.out_of_scope: la pregunta está fuera del alcance del visor.
  • chat.no_response: no se encontró una respuesta con los datos disponibles.
  • chat.llm_error: el proveedor del LLM falló o no está disponible.

Si borras uno, el chat usa el texto hardcodeado. No cambies el tono ni el contenido sin probar el flujo real.

Claves que usa el chat: chat.out_of_scope, chat.no_response y chat.llm_error.

Datos no disponibles

Inventario que usa el chat para responder con honestidad.

Datos no disponibles

Catálogo de indicadores que el visor no tiene. El chat lo consulta para decir “no hay datos” en lugar de inventar una respuesta.

  • Clave: identificador estable, por ejemplo aptitud_cultivos.
  • Descripción: qué dato falta, en lenguaje del usuario.
  • Palabras clave: términos que activan la detección (separados por coma).
  • Capas relacionadas: capas que se parecen al dato pedido.
  • Motivo: dato_inexistente (no existe la fuente), sin_receta (existe el dato pero falta el análisis) o fuente_no_ingerida (falta cargar el documento).
  • Origen: manual, catalog, ingest o recipe; indica de dónde salió el registro.
  • Activo: si está apagado, el detector lo ignora.

Al guardar se actualiza la fecha de verificación. Revisa el dato antes de marcarlo como no disponible.

Motivo: dato_inexistente (no existe), sin_receta (existe pero falta análisis) o fuente_no_ingerida (falta cargar el documento).

Golden set

Casos de evaluación del chat. Se ejecutan con npm run eval:chat.

Golden set

Casos de regresión que se ejecutan con npm run eval:chat (o node scripts/run-golden-set.mjs --all). El runner lee esta tabla y cae al archivo server/chat/__evals__/golden.json si no hay BD o si usas --from-json.

  • ID: identificador único del caso.
  • Pregunta: lo que se le envía al chat.
  • Level 1-3: profundidad de la evaluación (1 = smoke, 3 = análisis complejo).
  • Tier 1-6: capacidad esperada del modelo/ruta.
  • Expected: objeto JSON con los checks: tools_any, reply_must_contain, geojson_required, etc.
  • History: historial de conversación opcional, en JSON.
  • Activo: solo los activos se ejecutan.

Antes de cambiar un caso que pasa: copia su expected como plantilla y corre el runner para confirmar que sigue pasando. Un caso mal escrito hace fallar la evaluación sin que el chat esté roto.

tool = datos; rag = documentos; mixta = ambos; abstención = sin evidencia; fuera de alcance = rechazo.

Objeto JSON con los checks del caso. Copia el expected de un caso existente como plantilla.

Herramientas del chat

Inventario de solo lectura. Las tools son código y RPCs tipadas.

Herramientas del chat

Una tool es una función tipada que el orquestador puede invocar para consultar datos. El inventario es de solo lectura: las tools son código y RPCs, no configuración.

  • Cada tool vive en un archivo de server/chat/tools/ y se registra en server/chat/tools/index.js.
  • El LLM nunca escribe SQL: solo elige una tool y sus argumentos.
  • Agregar o cambiar una tool requiere código, tests y deploy; no se hace desde el panel.

Si una tool no aparece o falla, revisa el registro y sus tests. No la dupliques en el panel.

Cola de demanda

  • Rechazada / duplicada / archivada: no se trabajará.
