# Spec 08-A.5 — Tiles on-demand y cliente dinámico

| Campo | Valor |
|---|---|
| **Sprint (ROADMAP)** | 08-A.5 / 08-B dinámico |
| **Estado de la spec** | CERRADA (endpoint, caché y soporte cliente; sin capa dinámica en producción todavía) |
| **Tamaño** | Mediano |
| **Duración estimada** | 2-3 h |
| **Dependencias** | 08-A (Nginx, PostGIS), 08-B (cliente de tiles) |
| **Última revisión** | 2026-11-13 |

## 1. Objetivo y contexto

Las capas estáticas usan MVT pregenerado. Una capa **dinámica** (valores que
cambian o filtros que modifican la geometría) no puede congelarse en un tile:
necesita `ST_AsMVT` por request. Este tramo deja el esqueleto listo para cuando
exista la primera capa de ese tipo, sin migrar ninguna capa actual.

## 2. Alcance

**Dentro**
- `GET /api/layer-tiles?layer_id=&z=&x=&y=` con `ST_AsMVT`.
- Validación de `z/x/y` y de la capa contra el catálogo.
- 204 para tiles vacíos; 400/404 para errores.
- Caché Nginx por URL (`z/x/y`) con TTL 5 min y `proxy_cache_lock`.
- Cliente `leaflet.vectorgrid` con `tiles.mode: "on-demand"`; URL template con
  `{z}/{x}/{y}`, `bbox` opcional para `bounds`, sin manifest.
- Prueba del cliente con `borde_costero` en modo on-demand (temporal).

**Fuera**
- Una capa dinámica real (no existe todavía en PostGIS).
- Filtros server-side que cambian la geometría (el cliente filtra estilos).
- Optimización de concurrencia y límites por usuario.
- Streaming o tiles vectoriales para puntos.

## 3. Contrato del endpoint

```
GET /api/layer-tiles?layer_id=<id>&z=<0-18>&x=<0..2^z-1>&y=<0..2^z-1>
```

- Resuelve tabla/geometría/columnas desde `chat.chat_catalog`.
- SQL: `ST_TileEnvelope` + `ST_Transform(geom,3857)` +
  `ST_AsMVTGeom(...,4096,256,true)` + `ST_AsMVT`.
- `Content-Type: application/vnd.mapbox-vector-tile`.
- `Cache-Control: public, max-age=60`; Nginx cachea 200/204 con
  `X-Cache-Status`.
- 204 si el tile no tiene features; 400 si `z/x/y` es inválido; 404 si la capa
  no existe.

## 4. Cliente

```js
source: {
  type: "postgis",
  idColumn: "fid",
  tiles: {
    mode: "on-demand",
    layerName: "<layer>",
    urlTemplate: "/api/layer-tiles?layer_id=<layer>&z={z}&x={x}&y={y}",
    minZoom: 0,
    maxZoom: 16,
    bbox: { minx, miny, maxx, maxy }, // opcional, para bounds
  },
  fallback: { type: "geojson", url: "<layer>.geojson" },
}
```

- `isVectorTileLayer` acepta `static` y `on-demand`.
- En on-demand no se pide manifest; se usan `minZoom/maxZoom/bbox` de la config.
- El filtro de atributos se sigue aplicando en la función de estilo (cliente).

## 6. Validación realizada

- `curl` z10/308/596 → 200, 1.583 bytes; decoder MVT: capa `borde_costero`,
  90 features.
- Segunda request → `X-Cache-Status: HIT`.
- Tile z14/0/0 → 204; z19 → 400.
- `borde_costero` en modo on-demand en el visor: 2 requests, canvas con
  95.248 píxeles pintados y estilo aplicado. Luego se revirtió a static.

## 7. Riesgos y pendientes

- **Costo por tile:** `ST_AsMVT` usa CPU de PostgreSQL; solo para dinámicas.
- **Concurrencia:** falta un límite/cola global; Nginx `limit_req` y caché
  mitigan.
- **Filtros geométricos:** hoy no viajan al endpoint; se resuelven en cliente.
  Si cambian qué geometrías entran, agregar `filter` al contrato.
- **Capa dinámica real:** no hay ninguna poligonal/línea en PostGIS. Las
  estaciones son puntos con valores dinámicos por API (`stationsMapUtils`) y no
  usan tiles. El esqueleto queda listo para ARClim/indicadores cuando se
  ingesten como capas poligonales.
